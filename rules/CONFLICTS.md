# Conflicts between the rule sources, and the choice made

Every contradiction found while writing `business_rules.md`, with the choice the rulebook makes. The tie-break order was: the date-basis decision of 2026-11-07, then the franchise report pages, then production's slow-path prompt (what arms A and B run, since both have the recipe fast path off), then the recipes.

**Sources read (2026-11-07).**
- `SAAS/` = `Inspired Closets SAAS Reporting/` (read-only). Line numbers refer to the working copy on disk, which is HEAD `9ef5e4f` plus uncommitted "Step 0" edits (rule 14 and `SALES_BASIS` / `{SALES_DATE}` in `franchise-rules.ts`, `route.ts`, `system-dax.ts`, `system-vision.ts`, `dax-recipes.ts`, `recipe-matcher.ts`). `@HEAD` marks a line number in the committed version.

- `RPT/<ENT>/<page>` = `Power BI Report/per_entity/<ENT>/Salesforce BI <ENT>.Report/definition/pages/<page>/`.
- `WR/` = `sql/procedures/weekly_report/`.
- Data checks ran on the sandbox (2026-11-07 dump), schemas `poc_icla`, `poc_icch`, `poc_icau`.

**State note.** `PREREGISTRATION.md` describes A0 as `d1b6a70` and the A/B code base as production plus "the uncommitted 2026-11-07 work". ## A. Sales date basis

1. **Default basis for "sold" questions.**
   - `SAAS/lib/copilot/system-dax.ts@HEAD` L324-325: default Created Date for everyone; Original Project Sold Date only for "sold in <year>", "sold this year", "what we sold" or Salesforce tie-outs.
   - `SAAS/app/api/copilot/route.ts@HEAD` L122, L918-920: sold date for ICAU, ICCH, ICDF, ICSE, ICTA "for ANY 'sold' amount/count/ranking"; ICLA created.
   - `SAAS/lib/copilot/franchise-rules.ts@HEAD` L16, L31: ICAU and ICLA "Report date basis: CREATED date"; L22: ICCH SOLD.
   - `WR/sp_build_scorecard.sql` L24-34, `WR/sp_build_designer_leaderboard.sql` L6-9, `WR/sp_build_lead_source_roi.sql` L7: sold date except ICLA.
   - Choice: the decision (ICLA created, ICCH and ICAU sold), which matches route.ts, the weekly report and the Step 0 working copy (`franchise-rules.ts` L12-38, `system-dax.ts` L324-326, L540).
2. **"Sold in <year>" and person sales for ICLA.** `system-dax.ts@HEAD` L325 sends "sold in <year>" / "sold this year" / "what we sold" to the sold date for every franchise, and rule 6 (`system-dax.ts@HEAD` L532, `system-vision.ts@HEAD` L96) puts a person's "this year" on Original Project Sold Date for every franchise. Both contradict the decision for ICLA. Choice: the decision; the word "sold" does not switch the basis, only an explicit "by sold date" / "created" request does (working copy `system-dax.ts` L324, L532; rulebook section 4). For ICCH and ICAU there is no conflict.
3. **Briefing block still says Created Date.** `system-dax.ts` L49 (unchanged in the working copy) says "Sold/revenue metrics anchor on Salesforce_Data[Created Date] (matches the official weekly report)", while the same block's queries now filter `{SALES_DATE}` (L56-58, L62-64, L73, L79-80, L94-95) and the weekly report uses sold date for ICCH and ICAU. Choice: sales basis per the decision.
4. **Cookbook and DAX rules still default "this year" sales to Created Date.** `system-dax.ts` L225-227 (#1 sold this year), L236 (#2 designers this year), L250-251 (#4 variance), L463 ("how many sold this year" → Created Date), L505-506 ("Created Date is the active date column"; "current year" = `YEAR(Created Date)`); `system-vision.ts` L50, L53, L86. They contradict rule 14 (L540) for ICCH and ICAU. Choice: rule 14; the bindings' cookbook uses `{SALES_DATE}` for sales.
5. **Variance playbook.** `SAAS/lib/copilot/variance-playbook.ts` L37-38 filters sold revenue periods on Created Date. Choice: sales basis (bindings section 10).
6. **Recipes before Step 0.** `dax-recipes.ts@HEAD` REV-002 (L876), CNT-001, DSG-001 and others filter sold figures on Created Date for every branch, and the fast path never saw the CONTEXT basis (`route.ts@HEAD` L701-707), so a recipe and the LLM could answer the same question on different bases. The working copy fixes both (`{SALES_DATE}` in the 19 recipes tagged `salesBasis: "franchise"`; basis note at `route.ts` L705-718, L777-784). Not relevant to arms A and B (fast path off); relevant to A0.
7. **Report pages vs the decision.**
   - ICAU's visible "Pipeline Report" and "Lead Source Report - Created Date" (`RPT/ICAU/c14c75d09b437200da3b`, `RPT/ICAU/57caeef8ffb00dd9`, year slicers on `DateTable`) are created-date pages; the sold-date twins are hidden. The decision puts ICAU sales on sold date.
   - ICLA's KPI Overview (`PBI/ICLA/_measures.tmdl` L876-1069, `KPI Page HTML v2`: sold $, jobs and the closing tile on Original Project Sold Date) and Goals page (`PBI/ICLA/_measures.tmdl` L316-319, "Basis: SOLD DATE") use sold date; the decision puts ICLA sales on created date.
   - Choice: the decision; the basis line in every sales answer is what explains the mismatch (rulebook section 4).
8. **Sold-date coverage (production silent).** Sold dates exist only from mid-2023 (sandbox: ICAU sold projects by sold year 2023: 259, 2024: 605, none earlier; 2,865 / 3,051 / 2,030 Sold rows in ICLA / ICCH / ICAU have no sold date, nearly all created before 2023). `WR/sp_build_scorecard.sql` L24-29 only claims 2026 completeness. No prompt mentions the gap, so a sold-basis answer for 2022 comes out near zero. Choice (new rule, flagged for the project owner): keep the franchise basis but say most earlier sales have no sold date and give the created-date figure alongside; the same caveat for closing rates before 2024 and "all time" (C1 all time for ICLA is 21.5% because of it).
9. **Sale cycle period (production silent).** `[Av Cycle]` (`system-dax.ts` L442-444) has no basis rule, and the DAX rules default periods to Created Date (L505-506). Choice: a sale cycle for a period follows the sales basis (it describes sales).

## B. Closing rate

10. **Which definition is the default.**
    - Slow path: `system-dax.ts` L328 prefers `[Closing Rate]` (C1) for "closing %", "conversion %", per-designer closing and Salesforce tie-outs; `WEEKLY_TABLES_BLOCK` (`system-dax.ts` L128, `system-vision.ts` L153) uses C1 "this year to date when no period is named".
    - Fast path: `dax-recipes.ts` WK-CLOSE (L385-414), first in recipe order, answers a bare "what is our closing rate" with the weekly count-based rate (C4), current_ytd as the headline; CLS-001 (L2037-2075) and DSG-017 (L1992-2035) use C1 over a rolling last 4 months.
    - Briefing: `system-dax.ts` L51, L112: "CLOSING RATE is ALWAYS count-based" (C4).
    - Report: the created-date Pipeline Report page's "Closing % by designer" is C1 (`RPT/ICAU/c14c75d09b437200da3b/visuals/closing_rate_table`, same in ICLA and ICCH).
    - Choice: C1, year to date when no period is named (production's slow-path default, which arms A and B run, and the main Pipeline page); C4 for "this week" / "this month" / weekly report / briefing; C1 over 4 months only when asked; every answer names the definition and window.
11. **"This month" closing rate.** `system-dax.ts` L328 windows `[Closing Rate]` on the whole CONTEXT month for "this month"; `WEEKLY_TABLES_BLOCK` L128 sends "this week / this month" scorecard questions (closing_rate included) to the weekly tables (C4, month to date); WK-CLOSE matches "closing rate this month". Choice: C4 from the weekly report for this week and this month, C1 for any other named period.
12. **"Conversion rate".** `system-dax.ts` L328 maps "conversion %" to `[Closing Rate]`; recipe CNV-001 (`dax-recipes.ts` L1213-1235) maps "conversion rate" to `[Lead Conversion Rate]`; the model lists "Close Rate" as a synonym of both `[Closing Rate]` (`PBI/ICLA/_measures.tmdl` L87) and `[Lead Conversion Rate]` (`PBI/ICLA/_measures_L&A.tmdl` L11, which also lists "Success Rate"); the Opportunities page's "Conversion Rate" card is `[Lead Conversion Rate]` (`RPT/ICLA/66460a7531daa144c625/visuals/kpi_conversion_rate`). Choice: the report page; bare "conversion rate" = lead conversion rate, conversion of projects, designers or sales = closing rate, "success rate" = appointment success rate.
13. **Which closing rate ICCH sees.** `semantic-knowledge.ts` L545 reserves `[Closing Rate (Cohort)]` (C2) for Dallas/Fort Worth, but ICCH's visible "Pipeline Report - Sold Date" page shows C2 in its "Closing % by designer" table (`RPT/ICCH/db9770ed58e991cccd07/visuals/752a4a9fc5d1db144592`). Choice: C1 stays the default for ICCH; C2 when the user refers to that page or to "cohort" / "Closing & Amount". On 2026 YTD the two agree for ICCH (57.3%, it has no 2026 Dead Leads), so the impact is small.
14. **Other closing-like ratios in production, not adopted:** CNV-010 "sold conversion" = `[Count Sold]` ÷ `[Count Total Projects]` with Proposed in the denominator (`dax-recipes.ts` L4190); the ICLA Goals page's "sold/created excl Dead Lead" on sold date (`PBI/ICLA/_measures.tmdl` L319), a C2 variant.
15. **Scorecard label.** `WR/sp_build_scorecard.sql` L210-230 labels `lead_conversion` "Lead to Sold conversion" but computes leads with status Moved to Studio ÷ leads. Choice: call it lead conversion rate (moved to studio).

## C. Time scope and periods

16. **No period named.** The TIME SCOPE hard rule (`system-dax.ts` L332-370) says no time words means all time; `WEEKLY_TABLES_BLOCK` L128 makes closing rate year to date when no period is named. Choice: all time, with the closing-rate exception (plus rule 6 and the ICLA appointment floor).
17. **"This month vs last month".** The measure picker (`system-dax.ts` L436-440) compares whole calendar months; the briefing (`system-dax.ts` L70-73) and the weekly report (`WR/sp_build_scorecard.sql` L9-23) compare month to date with the same days of the prior month. Choice: calendar months unless the user says "same period" / "to date" or asks for a briefing; weekly-report metrics keep the report's windows.
18. **"This week" (production silent on the definition).** The weekly report's current week is the 7 days ending on the report date (`WR/sp_build_scorecard.sql` L14-16); the KPI Overview's week to date starts on Sunday (`PBI/ICLA/_measures.tmdl`, `KPI Page HTML v2`); the reports' weekly charts group by Sunday week starts. Choice: Sunday-to-Saturday weeks, except weekly-report metrics, which use the report's 7-day window and say so.
19. **Clock.** The CONTEXT date comes from the UTC clock (`route.ts` L911-914); recipes, the briefing block and the KPI page use `TODAY()` (service clock); MySQL `CURDATE()` is Pacific and the sandbox is frozen. Choice: an explicit franchise-local anchor date; both bindings forbid `TODAY()` / `CURDATE()`.

## D. Appointments

20. **Period column.** Rule 11 (`system-dax.ts` L537, `system-vision.ts` L101) filters appointment periods on Appointment Start Time; `[Current Month Activity Count]` (`semantic-knowledge.ts` L579, `PBI/ICLA/_measures_L&A.tmdl` L285), the KPI Overview's first appointments (`PBI/ICLA/_measures.tmdl` L913-916) and the weekly appointment funnel (`WR/sp_build_appointment_funnel.sql` L34-36, L60-62) use Activity Date and Time. Choice: Appointment Start Time (rule 11 and the Appointments pages' calendar).
21. **Weekly tables vs franchise appointment rules.** `WEEKLY_TABLES_BLOCK` L128 prefers `report_appointment_funnel` for "this month" appointment questions; that table counts raw entries for every franchise. `franchise-rules.ts` L60 says ICLA's rule applies to ANY appointment count; recipe APT-003 (`dax-recipes.ts` L1657-1677) counts every row for every branch. Choice: the franchise rule from the report pages, always; the weekly funnel only when asked for by name.
22. **Real appointments.** `semantic-knowledge.ts` L208 ("Column exists in all 9 franchise models") and L566 (other franchises should use the inline filter) vs `franchise-rules.ts` L66, L70 ("Only Seattle and Tacoma have this classifier") and `tools/pdf_report/recipients.py` `REAL_APPT_ENTITIES`. The column is populated for every franchise in the data. Choice: not reported for ICLA, ICCH or ICAU.
23. **Measures that look for stage values that don't exist.** `[Proposed Project Count]` (`PBI/ICLA/_measures_L&A.tmdl` L230; `semantic-knowledge.ts` L574) and `[Opportunities to Propose %/Count]` filter `Project Stage = "Propose"`, but appointment and bridge stages use "Proposed" (sandbox: ICLA 149, ICCH 210, ICAU 508 appointments), so they are always blank, as is the Appointments page's "Proposed" card. `[Staff Success Rate]` (`_measures_L&A.tmdl` L254) needs "Complete", which never occurs. Choice: score the intent (stage "Proposed"); never use Staff Success Rate.
24. **ICLA Opportunities pages.** `franchise-rules.ts` L61 tells the bot the Opportunities pages apply appointment filters (activity type, staff list, project stage). Those page filters exist (`RPT/ICLA/66460a7531daa144c625/page.json`, `RPT/ICLA/01ca6b82c78f7049/page.json`), but every visual on those pages counts leads, and no relationship lets an `Appointments` filter reach `Leads`, so they change nothing that is shown (inference from the relationship graph, not verified by running DAX). Choice: leads are counted as-is; the filters are not applied to anything. The staff list there has 13 names, the same as the Appointments pages (the research notes say 12).
25. **ICLA count in the prompt.** `franchise-rules.ts` L7 says the report showed 673 first design appointments since 2026, L60 says 675. The sandbox gives 675 with the full rule. No rule change.

## E. Designers, stages, names

26. **Two designer rosters.** Per-designer closing rate groups by the active-only `dim_designers` (`system-dax.ts` L328, DSG-017, the report's "Closing % by designer"), while sales rankings group by `Salesforce_Data[Designer]` (cookbook #2 `system-dax.ts` L230-239, DSG-001), which includes inactive and x-prefixed names (ICLA has 4,366 rows with x-prefixed designers). Choice: keep both, as production does: sales by the project's designer, closing rate per designer on the active roster.
27. **Blank and unassigned designers (production silent).** The prompts never say what to do with a blank designer; the weekly leaderboard drops blank designers and keeps those with at least 5 projects created or 1 sale this month (`WR/sp_build_designer_leaderboard.sql` L53, L59). Choice: unassigned projects never ranked as a designer, kept in totals; the active roster's blank row ("inactive or unassigned designers") left out of rankings.
28. **"Active designers".** DSG-016 (`dax-recipes.ts` L1067-1100: active roster with at least one project) and DSG-002 (L1102-1125: every roster member) both match "who are the active designers"; CNT-009 (L4045-4060) counts "active designers this year" as distinct designers on projects created this year; the KPI page counts distinct designers on projects created this month. Choice: "list the active designers" = roster with at least one project; "how many designers were active" in a period = distinct designers on projects created in it.
29. **Revised Stage mapping.** `semantic-knowledge.ts` L65 says Proposed "was Propose/Design/Incomplete"; the Gold procedure (`sql/procedures/gold/sp_gold_build_fact_sales.sql` L78-90, rev 2026-11-05) and the data map Incomplete to Sold (`sql/CLAUDE.md` L72 is also stale). Choice: the data.
30. **"Opportunities" means two things.** Production treats `Salesforce_Data` as opportunities (`semantic-knowledge.ts` L59); the report's Opportunities page titles its lead count "Total Opportunities" (`RPT/ICLA/66460a7531daa144c625/visuals/kpi_leads`). Choice: projects / opportunities = opportunity rows; the Opportunities page's figures are leads.
31. **Sold-date mechanism.** `semantic-knowledge.ts` L71 and L607 tell the model to activate the inactive DateTable link with USERELATIONSHIP for sold-date analysis; L350, L608 and `franchise-rules.ts` L21-25 use the active `SoldDateTable` link. Both give the same numbers. Choice (DAX bindings): `SoldDateTable` or a direct column filter; no USERELATIONSHIP.

## F. Averages and counts

32. **"Average project value".** The measure picker (`system-dax.ts` L398-401) uses a plain `AVERAGE(Amount)` for "average project value across all" and `[APV]` (deals over $1,000, all stages) only for "significant deals"; the Lead Source pages' "Avg project value" card is `[APV]` (`RPT/ICCH/20e8a17e7054daac5701/visuals/kpi_apv`, `RPT/ICLA/57caeef8ffb00dd9/visuals/kpi_apv`, `RPT/ICAU/57caeef8ffb00dd9/visuals/kpi_apv`); the weekly report's `apv_sold` is the average sold value, labelled "Avg project value (Sold)" (`WR/sp_build_scorecard.sql` L95-120). Choice: average project value with no qualifier = average sold value (the weekly report's APV); plain average for "per opportunity" / "across all projects"; the $1,000 rule only when the card or "significant deals" is named. Flagged as a judgement call: the question is ambiguous in production.
33. **Distinct counts.** The measure picker uses `DISTINCTCOUNT`, which counts a blank as a value (`system-dax.ts` L394-396). Choice: blanks never counted (`DISTINCTCOUNTNOBLANK` / `COUNT(DISTINCT …)`). No current effect: the three franchises have no blank designers or lead sources.
34. **Last-activity cookbook shape.** `system-dax.ts` L491-492 summarises `Salesforce_Data` by Project Name and Amount, which merges two projects with the same name and amount. Choice: the bindings key the list on Project ID (one row per project).
35. **Year-over-year measures.** The measure picker says "last year revenue" must use an explicit year filter, not `[Revenue Previous Year]` (`system-dax.ts` L403-405), but prefers `[Revenue YoY Growth]` for "yoy sold revenue growth" (L467-469). `[Revenue YoY Growth]` is `[Total Revenue] - [Revenue Previous Year]` (`PBI/ICLA/_measures.tmdl` L176-199): all stages, not sold, and built on the measure L403-405 rejects. Choice: explicit windows on the right basis for every year-over-year question; the time-intelligence measures are never used (both bindings, section 2).

## G. Not verified here

- The DAX patterns in `dax_bindings.md` were not run (no Power BI access in this task). The measure bodies are copied from the TMDL, and most query shapes come from production's cookbook, which its audit script ran on all six datasets; the new shapes (calendar breakdown with the blank year removed, `TREATAS` for appointments on sold projects, C3 inline, C4 inline, per-designer C1 with `NOT ISBLANK`, the Project ID last-activity list) still need one run each.
- `MEDIANX` blank handling: the JN Days measures filter `[Days to …] >= 0`, and a blank compares as 0 in DAX, so leads with no date pass that filter. The SQL binding takes the median over non-NULL values only. If `MEDIANX` counted those blanks the two routes would differ; check one JN Days value by DAX against the SQL median.
- Item 24 (ICLA Opportunities page filters have no effect) is an inference from the relationship graph.
